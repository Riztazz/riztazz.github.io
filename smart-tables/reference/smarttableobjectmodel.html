SmartTableObjectModel.h

The model behind Set Items. It holds the objects and reads them by name.

Source/SmartTables/Public/SmartTableObjectModel.h

The model SetItems builds, and the one most tables never name.

Rows are UObjects, and columns resolve by name to a property or to a pure function that needs no input, once per class. That is the whole path with no code behind it: text, sorting and filtering all fall out of the same resolved binding.

It owns its items, the way UListView holds a strong array. Items are usually built in a Blueprint and held nowhere else, so a model that only pointed at them would empty itself at the next garbage collection, in no fixed order.

BindingsByClass
TMap< TWeakObjectPtr< UClass >, TArray< FColumnBinding > > BindingsByClass

Keyed by item class, because a set holding several classes is fine. A column that resolves on some of them draws for those and stays empty for the rest, which is a fact about the data.

Weak, and swept on a miss inside FindBinding. A Blueprint compile gives the same objects a freshly built UClass. The entry for the class it replaced can never be found again, since a weak key is matched by its number, and the two writers that clear this map are not on that path. Without the sweep every compile leaves one dead entry behind, for the life of the model.

ColumnOrderById
TMap< FName, int32 > ColumnOrderById

Column id to its place in Columns. Filled in SetColumns, so it holds for every class at once: the binding arrays are all in the same order as Columns. A cell draw would otherwise walk the columns to find its own, once per cell per frame.

RowByItem
TMap< TObjectKey< UObject >, int32 > RowByItem

Item to its row, so IndexOfItem is a lookup and not a walk of every item.

Every writer of Items writes this in the same call, and there are five. SetItems and MoveRows rebuild it. RemoveItem rebuilds it too, since taking one out moves every row after it. ClearItems empties it, and AddItem adds the one row it appended.

A writer that forgets leaves the table scrolling to the wrong row and selecting nothing, and says nothing anywhere.

The FIRST of a repeated item holds the row, which is what a walk of the items answered.

FColumnBinding struct

The bindings of one column against one item class. Resolved per class and never per cell, or a table of ten thousand rows would do ten thousand name lookups to draw one column.
