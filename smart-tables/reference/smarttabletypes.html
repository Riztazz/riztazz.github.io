FSmartTablePresentationChange struct

What moved in the presentation of a model, as separate facts.

Flags and not a scale. Every visible cell being stale and the row set having moved are two pieces of work, and Add ORs them so neither is ever dropped while a rebuild is out.

A live data sweep arriving while a dispatched sort still holds an older presentation has to keep both halves. One number could carry only the wider of the two, and rows that did not move would go on drawing values that did.

Not a USTRUCT: it goes through a plain C++ delegate, and nothing authors or saves it.

How much this reaches, worked out from every field at once.

The one place the fields become an answer. A row number or a column id beside a moved order counts for nothing, since the whole screen is stale either way.

Add
void Add( const FSmartTablePresentationChange & Other )

Folds Other in, losing nothing.

Every flag either side set stays set. Changes add up while a rebuild is out, and they go out together no matter how many arrive.

A row number lives on only while it is the only one in play. Two different rows, or a row beside anything wider, is no longer about one row, and saying otherwise would refresh one and skip the rest.

The column is nested inside that rule and never folded beside it. One column in two rows is two rows, so the column goes wherever the row number goes.

One field and never three half answers. It picks which of ExpectedItemClass, SourceTable and SourceFile the panel shows. It also picks the struct behind the binding dropdown, the struct the compile checks against, and the source the column builder reads.

This is what an entrance animation reads. All four arrive as the same call with the same arguments, and only the reason tells them apart. A table scrolling a million rows reassigns constantly, and an entrance played on every one of those flashes instead of animating.
